### 1. Product Summary

A mobile-first web app for a small private household group to manage a shared grocery list. The app should make it fast and low-friction to add items, review what needs to be bought, and remove items after shopping.

The product is intentionally narrow in v1. It is not a full household organizer in the first release.

*This document builds the foundation for the [[Technical Architecture]] doc.*

---

### 2. Problem

**People sharing a household often do not have one reliable, current view of what groceries still need to be bought.**  **This leads to:**

1. missed items
2. duplicate purchases
3. extra messaging overhead
4. friction when trying to update the list quickly on a phone

---

### 3. Target Users

#### Primary users:

- Small private households
- 2 to 5 active users maximum
- Smartphone-first usage
- Users are not assumed to be technical

#### Core user need:

- See the current shared grocery list immediately
- Add an item in a few seconds
- Mark collected items during shopping
- Avoid confusion when multiple users edit the list

---

### 4. Product Goals

#### Primary goal

- Create a reliable shared grocery list that is fast to use on a smartphone and easy to maintain.
- Success criteria for v1
  - A user can add a new item in under 10 seconds
  - The list state remains correct when multiple users edit it
  - Users can complete a shopping trip without needing separate chat messages for list coordination
  - The app is stable and understandable enough for daily use

#### Non-goals for v1

- No weekly meal planner
- No notes section
- No shopping history analytics
- No recommendation engine
- No push notifications
- No offline-first sync system

---

### 5. Version Scope

#### v1 — MVP

**The MVP includes only the features required to solve the grocery-list problem well.**

**In scope:**

- Household creation and member login
- Shared grocery list
- Add item flow with search/suggestions
- Manual favorites for common items
- Check/uncheck items during shopping
- Explicit confirm action to remove checked items permanently
- Basic conflict-safe multi-user behavior
- Mobile-first UI

**Out of scope**

- Calendar / weekly meal planner
- Notes
- Usage statistics
- “Most frequently added” auto-favorites
- Smart shopping suggestions

#### v2

**Once v1 is stable and genuinely useful, expand into adjacent household planning features.**

**Planned v2 features:**

- Weekly meal planner
- Notes section
- Shopping history
- Auto-suggested favorites based on usage
- Simple statistics such as most-bought items

### 6. Resolved Product Decisions

#### 6.1 MVP boundary

- The app is a shared grocery app first. Meal planning and notes are explicitly deferred to v2.

#### 6.2 Favorites model

- Favorites in v1 are manual household-wide shortcuts, not auto-generated by frequency.
- Reason:
  - simpler to implement
  - more predictable for users
  - no need for analytics/history tables in v1

#### 6.3 Search behavior

- The add-item search supports:
  - case-insensitive prefix match
  - case-insensitive substring match
- Search suggestions come from:
  - household favorites
  - previously used item names
- Users can also add a completely new custom item if no suggestion matches.

#### 6.4 Item duplication behavior

**To keep the list clean:**

- Only one active item with the same normalized name + unit + note should exist at a time.
- If a matching active item already exists, the app increments its quantity instead of creating a duplicate row
- Example:
  - adding “Milk, 1 bottle” twice results in one entry with quantity 2 bottles

#### 6.5 Quantity model

- The item amount is semi-structured.
- Each item has:
  - name — required
  - quantity_value — numeric, default 1
  - unit — optional short text such as pcs, g, kg, bottle, pack
  - note — optional short text such as whole grain, brand X

**This is more maintainable than a single raw text field, while still flexible enough for groceries.**

#### 6.6 Deletion / shopping workflow

**The list supports a reversible shopping flow:**

- users check items while shopping
- checked items move to a staged “done” state
- checked items remain reversible until confirmed
- pressing “Confirm purchase” permanently removes all currently checked items

This preserves the benefit of reversible staging without introducing unnecessary complexity.

#### 6.7 Conflict handling

- No queue-based locking in application code.
- Instead:
  - each write happens in a database transaction
  - latest committed state is the source of truth
  - if two users edit at nearly the same time, the final committed action wins
  - the UI refreshes after each write and also periodically while the page is open
- This is simpler and more reliable than an in-process Python queue.

#### 6.8 Authentication model

- Use simple local authentication.
- Username + password
- Password hashes stored securely
- One user is household owner
- Other users join via invite code
- No OAuth in v1
- Reason:
  - private small-scope app
  - fewer moving parts
  - easier to maintain

#### 6.9 Real-time update model

- No WebSockets in v1.
- Instead:
  - refresh list after each successful action
  - refresh on page focus
  - optional light polling every 15–30 seconds on the grocery page
- This is enough for a max-5-user household app.

### 7. Core Features for v1

#### 7.1 Authentication and household setup

##### Description

A user creates a household and becomes owner. Other members join using an invite code.

##### Requirements

- user registration with username and password
- household creation during first setup
- invite code generation by owner
- member joins household using invite code
- maximum 5 active users per household

##### User value

Simple setup without email or third-party login dependencies.

---

#### 7.2 Grocery list overview

##### Description

The main list of all active grocery items.

##### Behavior

- active items shown first
- checked items shown below active items, visually greyed out and crossed out
- items sorted alphabetically within each section
- each item shows:
  - name
  - quantity
  - optional note

##### User value

Immediate overview of what still needs to be bought.

---

#### 7.3 Add item flow

##### Description

A search/input field at the top of the grocery page allows fast addition of items.

##### Behavior

- user types item name
- dropdown shows matching favorites and previously used items
- user selects a suggestion or creates a new item
- user sets quantity, optional unit, optional note
- item is saved immediately
- if same active item already exists, quantity is incremented

##### Acceptance criteria

- empty item names are rejected
- very long input is rejected
- control characters / unsafe HTML are rejected
- letters, spaces, numbers, hyphens, apostrophes, umlauts and accents are allowed
- Important: v1 should not ban numbers or special characters broadly, because grocery items often require them.

---

#### 7.4 Favorites

##### Description

Household-wide manual shortcuts for commonly used items.

##### Behavior

- users can add an active grocery item to favorites
- users can remove favorites
- users can reorder favorites
- the main grocery page shows the first 8 favorites as quick-add buttons
- tapping a favorite opens a minimal quantity prompt, then adds it to the list

##### User value

Reduces friction for common recurring items.

---

#### 7.5 Check / uncheck items

##### Description

Items can be toggled into a staged “done” state during shopping.

##### Behavior

- checking an item sets status to checked
- unchecking reverts it to active
- change is persisted immediately
- other users see the updated state after refresh/polling

##### User value

Makes the list useful during an actual shopping trip.

---

#### 7.6 Confirm purchase

##### Description

A dedicated action permanently removes all checked items.

##### Behavior

- “Confirm purchase” deletes all currently checked items in one transaction
- action affects the shared household list
- after success, list reloads in current state

##### User value

Preserves reversible staging during shopping, then allows clean reset afterward.

---

### 8. User Flow

#### Happy path

1. User opens app at the supermarket
2. User reviews active grocery items
3. User collects items and checks them off
4. If needed, user adds a forgotten item
5. After checkout, user presses “Confirm purchase”
6. Checked items are removed from the shared list

#### Concurrent edit path

1. Two users open the same list
2. One user adds or checks an item
3. The other user sees the change after action refresh, focus refresh, or periodic polling
4. If both act on the same item, the latest committed database state is shown after refresh

### 10. Technical Plan

#### Architecture

- Use a modular monolith.

#### Why

- simplest architecture that still scales to the actual need
- maintainable and testable
- avoids overengineering
- suitable for 2–5 active users

#### Stack

##### Frontend

- Server-rendered HTML with Jinja templates
- Tailwind CSS
- Small amount of JavaScript for interactivity
- HTMX for partial page updates

##### Backend

- Python
- Flask using app factory pattern
- Flask blueprints by domain:
  - auth
  - household
  - grocery
  - favorites

##### Database

- PostgreSQL
- SQLAlchemy ORM
- Alembic for migrations

##### Auth / security

- Flask-Login
- Argon2 or bcrypt for password hashing
- CSRF protection
- secure session cookies
- server-side input validation
- basic rate-limiting for login routes

#### Deployment

- Docker Compose
- Services:
  - web
  - postgres
- Optional reverse proxy if internet-exposed
- Suitable for a small VPS, home server, or Raspberry Pi-class deployment

### 11. API / Interaction Style

- Even though the app is server-rendered, internal route design should stay clean and resource-oriented.

Examples:

```
GET /grocery
POST /grocery/items
POST /grocery/items/<id>/toggle
POST /grocery/confirm
GET /favorites
POST /favorites
POST /favorites/<id>/reorder
```

- The UI should mostly call these endpoints through standard form posts or HTMX requests.
- No separate public REST API is required in v1.

### 12. Reliability and Maintainability Requirements

- clear domain separation via blueprints
- all writes wrapped in database transactions
- migrations managed explicitly
- minimal dependencies
- server-side validation as source of truth
- unit tests for model and service logic
- integration tests for major user flows
- structured logging for errors and key state changes

---

### 13. Risks and Mitigations

- **Risk: scope creep**
  - The original idea expands naturally into planner, notes, analytics.
  - Mitigation: strict v1/v2 split.
- **Risk: conflicting multi-user edits**
  - Multiple users may shop independently.
  - Mitigation: transactional writes, shared source of truth in Postgres, periodic refresh, last committed state wins.
- **Risk: accidental deletion**
  - Users may check the wrong item.
  - Mitigation: staged check/uncheck workflow, separate confirm step.
- **Risk: mobile usability**
  - Too many UI elements can make the app fiddly.
  - Mitigation: keep v1 focused on one main page, one search field, one clear list, one confirm action.
- **Risk: network interruptions**
  - Users may temporarily lose connection while shopping.
  - Mitigation: show clear error feedback on failed writes and keep UI interaction simple; offline mode is not part of v1.
